# План разработки прототипа по GDD

Источник требований: `GDD_prototype_gap_analysis.md`.

Цель документа: разложить разработку MVP на такие шаги, чтобы каждый шаг позже можно было превратить в отдельный промпт для реализации. На этом этапе документ не содержит готовые промпты, а задает порядок, границы задач, архитектурные решения и критерии готовности.

## 1. Итоговая цель прототипа

Нужно получить минимальный, но законченный playable loop:

`Base(stub) -> Run на 3 минуты -> Stop/Defeat -> начисление ресурсов -> Base(stub)`

Прототип считается успешным, если:

- игрок может начать забег с базы;
- в забеге есть движение, автоатака, враги, XP, уровни и выбор перков;
- работают две независимые шкалы поражения: `HP <= 0` и `Arousal >= 100`;
- есть 3 типа врагов: `melee`, `ranged`, `caster`;
- есть 6 перков уровня и 4 пассивки поражения;
- ресурсы начисляются по правилам `100%` при выходе через остановку и `30%` при поражении;
- состояние между забегами сохраняется;
- все игровые сущности рендерятся через текстуры или placeholder-спрайты;
- проект собирается через CMake под Windows/MSVC, MinGW остается best-effort.

## 2. Ключевое архитектурное решение: ECS

### 2.1 Почему ECS стоит использовать

Игра в жанре `Vampire Survivors-like` потенциально быстро приходит к большому числу однотипных сущностей:

- десятки или сотни врагов;
- снаряды игрока и врагов;
- pickup-объекты, XP, ресурсы;
- временные эффекты, хитбоксы, визуальные эффекты;
- будущие баффы, дебаффы и модификаторы.

Для такого проекта лучше сразу заложить легкий ECS-подход, но без сложного фреймворка. На этапе MVP достаточно собственной простой реализации:

- `EntityId` как числовой идентификатор;
- компоненты хранятся в плотных массивах или `unordered_map<EntityId, Component>`;
- системы обрабатывают только нужные наборы компонентов;
- создание и удаление сущностей выполняется через `World`/`Registry`;
- удаление сущностей откладывается до конца кадра, чтобы системы не ломали итерацию.

Это даст хороший баланс: производительность и расширяемость без преждевременной сложности.

### 2.2 Что не нужно делать в MVP

Не стоит внедрять полноценный сторонний ECS-фреймворк на старте, если проект начинается с нуля и требования еще меняются. Также не нужно сразу делать:

- archetype ECS;
- многопоточную обработку систем;
- сложный job scheduler;
- generic reflection/serialization всех компонентов;
- визуальный редактор сущностей.

MVP должен остаться простым для отладки.

### 2.3 Рекомендуемая структура ECS

Минимальные сущности:

- `Player`;
- `Enemy`;
- `Projectile`;
- `Pickup`;
- `DamageArea` при необходимости;
- UI и screens лучше не делать ECS-сущностями на первом этапе.

Базовые компоненты:

- `TransformComponent`: позиция, rotation при необходимости;
- `VelocityComponent`: скорость движения;
- `SpriteComponent`: ссылка на текстуру, rect, scale, tint;
- `ColliderComponent`: радиус или AABB;
- `HealthComponent`: current/max HP;
- `ArousalComponent`: current/max для игрока;
- `EnemyComponent`: тип врага, AI-параметры;
- `ProjectileComponent`: owner, damage, lifetime, speed/type;
- `AttackComponent`: cooldown, range, damage;
- `ExperienceComponent`: level, current XP, XP threshold;
- `PickupComponent`: тип и количество;
- `LifetimeComponent`: автоудаление через время;
- `DefeatPassiveComponent` не обязателен как ECS-компонент, лучше хранить пассивки в persistent state.

Основные системы:

- `InputSystem`;
- `MovementSystem`;
- `EnemyAISystem`;
- `AutoAttackSystem`;
- `ProjectileSystem`;
- `CollisionSystem`;
- `DamageSystem`;
- `PickupSystem`;
- `LevelUpSystem`;
- `PerkSystem`;
- `SpawnSystem`;
- `WaveSystem`;
- `RunTimerSystem`;
- `RenderSystem`;
- `CleanupSystem`.

## 3. Предлагаемая верхнеуровневая структура проекта

Так как проект начинается почти с нуля, можно заложить следующую структуру:

```text
VampireSurv_like/
  CMakeLists.txt
  CMakePresets.json
  assets/
    textures/
      placeholders/
  src/
    main.cpp
    app/
      Application.h/.cpp
      GameState.h

    core/
      Time.h
      Random.h
      Math.h
    ecs/
      Entity.h
      World.h/.cpp

    game/
      Balance.h

      SaveSystem.h/.cpp
      Perks.h/.cpp
      DefeatPassives.h/.cpp
    systems/
      MovementSystem.h/.cpp
      EnemyAISystem.h/.cpp
      CombatSystems.h/.cpp
```

Структуру можно упростить при реализации, но важно сохранить разделение:

- приложение и экраны;
- ECS core;
- игровые данные и баланс;
- системы симуляции;
- сохранение;
- загрузка ассетов.

## 4. Этапы разработки

Каждый этап ниже должен быть самостоятельным инкрементом. После выполнения этапа проект должен собираться и запускаться.

### Этап 0. Подготовка проекта и сборки

Цель: создать базовый C++/SFML проект, который стабильно собирается.

Задачи:

- добавить `CMakeLists.txt`;
- добавить `CMakePresets.json` для MSVC и MinGW;
- подключить `SFML 2.6.2` через `find_package`;
- настроить копирование DLL рядом с `.exe`;
- создать минимальный `main.cpp`;
- открыть окно SFML и корректно закрывать приложение.

Результат:

- команда сборки по MSVC-пресету проходит;
- приложение открывает пустое окно;
- в коде есть стартовая структура каталогов.

Критерии приемки:

- нет ручного копирования DLL после каждой сборки;
- путь MSVC является основным;
- MinGW-пресет существует, даже если проверяется позже.

### Этап 1. Application loop и экраны

Цель: заложить управление состояниями приложения.

Задачи:

- создать `Application`;
- ввести enum или state machine для экранов;
- реализовать `BaseScreen`;
- реализовать `RunScreen` как пустой экран;
- реализовать переход `Base -> Run -> Base`;
- добавить базовую обработку input и delta time.

Результат:

- игрок видит базу-заглушку;
- может начать забег;
- может вернуться на базу тестовой клавишей.

Критерии приемки:

- логика экранов не смешана с ECS;
- игровой цикл имеет фиксированное место для `update()` и `render()`;
- ввод обрабатывается централизованно или через понятный screen API.

### Этап 2. Минимальный ECS core

Цель: создать основу для большого количества игровых сущностей.

Задачи:

- реализовать `EntityId`;
- реализовать `World`/`Registry`;
- добавить создание и отложенное удаление сущностей;
- добавить базовое хранение компонентов;
- добавить первые компоненты: `Transform`, `Velocity`, `Sprite`, `Collider`;
- добавить простой способ итерироваться по сущностям с нужными компонентами.

Результат:

- можно создать сущность игрока;
- можно создать несколько тестовых сущностей;
- системы могут безопасно обновлять компоненты.

Критерии приемки:

- удаление сущностей не ломает итерацию;
- API ECS прост и не требует сложных шаблонов там, где они не нужны;
- компоненты не знают о SFML-окне и экранах.

### Этап 3. AssetManager и placeholder-графика

Цель: выполнить требование GDD о рендере текстур/спрайтов.

Задачи:

- реализовать `AssetManager`;
- загрузить placeholder-текстуры;
- если файлов пока нет, генерировать простые fallback-текстуры в памяти;
- реализовать `RenderSystem`;
- привязать `SpriteComponent` к текстурам;
- отрисовать игрока и тестовых сущностей.

Результат:

- все сущности отображаются как спрайты;
- отсутствие файла текстуры не приводит к падению приложения.

Критерии приемки:

- логика загрузки ассетов изолирована от игровых систем;
- рендер не изменяет игровую симуляцию;
- placeholder-ассеты позволяют продолжать разработку без финальной графики.

### Этап 4. Игрок: движение, HP, Arousal

Цель: сделать базового управляемого игрока.

Задачи:

- создать player entity;
- добавить движение WASD;
- ограничить игрока границами карты или временной игровой областью;
- добавить `HealthComponent` со значением `100`;
- добавить `ArousalComponent` со значением `0..100`;
- вывести базовый HUD: HP, Arousal, таймер.

Результат:

- игрок двигается;
- значения HP/Arousal отображаются;
- есть основа для поражений.

Критерии приемки:

- скорость игрока соответствует `220 px/s`;
- движение не зависит от FPS;
- HUD можно расширять под XP, ресурсы и перки.

### Этап 5. Враги melee и контактный урон

Цель: реализовать первый боевой контур.

Задачи:

- создать `EnemyComponent`;
- добавить тип `Melee Grunt`;
- реализовать спавн melee-врагов;
- реализовать преследование игрока;
- добавить collision/contact damage;
- добавить hit cooldown `0.9 s`;
- уменьшать HP игрока на `8`.

Результат:

- melee-враги появляются, идут к игроку и наносят урон;
- игрок может получить поражение по HP.

Критерии приемки:

- контактный урон не наносится каждый кадр;
- поведение врагов масштабируется на десятки сущностей;
- поражение по HP переводит из run в result/base flow.

### Этап 6. Автоатака игрока

Цель: дать игроку базовый способ убивать врагов.

Задачи:

- добавить `AttackComponent` игроку;
- реализовать автоатаку раз в `0.55 s`;
- искать ближайшего врага в радиусе `260 px`;
- наносить `16` урона;
- удалять врагов при `HP <= 0`;
- добавить простую визуализацию атаки или снаряда игрока.

Результат:

- игрок автоматически атакует ближайшего врага;
- враги умирают от урона.

Критерии приемки:

- атака использует cooldown, а не зависит от FPS;
- target selection отделен от нанесения урона;
- смерть врага корректно проходит через cleanup.

### Этап 7. XP, pickup и уровни

Цель: реализовать цикл убийства врагов и роста игрока.

Задачи:

- за убийство врага создавать XP pickup или начислять XP напрямую;
- для MVP предпочтительнее создать pickup, чтобы проверить систему столкновений;
- добавить XP значения: melee `10`, ranged `12`, caster `16`;
- реализовать формулу `XP_to_next = round(40 * level^1.25)`;
- при level up останавливать run и показывать выбор из 3 перков.

Результат:

- игрок получает XP;
- уровень повышается;
- появляется экран выбора перка.

Критерии приемки:

- выбор перка блокирует симуляцию run;
- после выбора run продолжается;
- XP threshold пересчитывается согласно формуле.

### Этап 8. Перки уровня

Цель: реализовать 6 MVP-перков.

Задачи:

- описать перки в данных, а не в разрозненном коде;
- реализовать пул из 6 перков:
  - `Power I`: +15% damage;
  - `Attack Speed I`: -12% attack interval;
  - `Vitality I`: +20 max HP и heal до нового max;
  - `Calm Mind`: -20 arousal;
  - `Momentum`: +10% speed;
  - `Range I`: +18% attack range;
- выбирать 3 случайных перка;
- применять выбранный перк к player stats.

Результат:

- level up дает осмысленный выбор;
- выбранные перки меняют параметры игрока.

Критерии приемки:

- перки работают через модификаторы или отдельную структуру stats;
- перки не требуют переписывать системы;
- повторное получение перков либо разрешено явно, либо запрещено явно.

Рекомендация для MVP: разрешить повторное получение простых перков, если это ускоряет разработку. В документе баланса можно позже ограничить стаки.

### Этап 9. Ranged и caster враги

Цель: довести врагов до GDD-scope.

Задачи:

- добавить `Ranged Archer`;
- добавить дистанционное поведение: держать расстояние и стрелять;
- добавить projectile damage `7`, speed `280`, cooldown `1.4 s`;
- добавить `Caster`;
- caster стреляет более толстым/отличимым снарядом;
- caster projectile damage `10`, speed `230`, cooldown `1.8 s`;
- реализовать lifetime и collision снарядов.

Результат:

- на карте есть 3 читаемых архетипа врагов;
- ranged и caster отличаются визуально и поведением.

Критерии приемки:

- projectile-сущности обрабатываются ECS-системами;
- снаряды удаляются при попадании или истечении lifetime;
- ranged AI не застревает при приближении игрока.

### Этап 10. Arousal damage и поражение

Цель: довести вторую шкалу поражения до полноценной механики.

Задачи:

- определить, какие атаки дают arousal damage в MVP;
- для прототипа можно сделать часть снарядов или caster projectile источником arousal damage;
- добавить применение arousal damage;
- реализовать поражение при `Arousal >= 100`;
- различать причины поражения: HP или Arousal.

Результат:

- обе шкалы независимо приводят к поражению;
- статистика может учитывать тип поражения.

Критерии приемки:

- HP defeat и Arousal defeat используют общий result flow;
- причина поражения сохраняется;
- arousal не выходит за диапазон `0..100`.

### Этап 11. Волны, таймер и stop screen

Цель: реализовать 3-минутный run и легальный выход.

Задачи:

- добавить run timer `3:00`;
- реализовать простую таблицу волн;
- после убийства последней волны или завершения таймера показать stop screen;
- добавить действия:
  - `Continue` как заглушка;
  - `Exit to Base`;
- остановить симуляцию на stop screen.

Результат:

- run имеет понятное завершение;
- игрок может выйти на базу с `100%` ресурсов.

Критерии приемки:

- stop screen не считается поражением;
- `Continue` явно помечен как MVP-заглушка;
- run timer не продолжает тикать на paused/choice screens.

### Этап 12. Ресурсы и экономика результата

Цель: реализовать правила выноса ресурсов.

Задачи:

- добавить сбор ресурса внутри run;
- хранить `runResourceRaw`;
- при stop exit начислять `100%`;
- при поражении начислять `30%`;
- сохранять `lastRunResourceRaw`;
- сохранять `lastRunResourceGranted`;
- обновлять `totalResource`.

Результат:

- после каждого run база показывает результат;
- экономика соответствует GDD.

Критерии приемки:

- округление `30%` определено явно;
- результат не начисляется дважды при повторном входе на экран;
- result flow покрывает stop и defeat.

Рекомендация: для MVP использовать `floor(raw * 0.3)` или `round(raw * 0.3)`, но выбрать один вариант и закрепить в коде. Более предсказуемый вариант для игрока - `floor`.

### Этап 13. Пассивки поражения

Цель: реализовать долгосрочное последствие проигрыша.

Задачи:

- описать 4 пассивки:
  - `Fractured Nerves`: +10% incoming HP damage;
  - `Sensitive Skin`: +15% incoming arousal damage;
  - `Heavy Steps`: -8% movement speed;
  - `Shaky Focus`: +12% attack interval;
- при каждом поражении выдавать 1 случайную пассивку;
- сохранять список пассивок;
- применять пассивки при старте следующего run.

Результат:

- поражение меняет будущие забеги;
- база отображает список полученных пассивок.

Критерии приемки:

- пассивки выдаются только при defeat, не при stop exit;
- пассивки сохраняются между запусками приложения;
- влияние пассивок видно в stats игрока.

Рекомендация для MVP: разрешить дубликаты пассивок, если GDD не запрещает стаки. Если дубликаты нежелательны, нужно явно определить поведение при полном пуле.

### Этап 14. Persistent state и save/load

Цель: сохранить данные между забегами и запусками.

Задачи:

- создать `PersistentState`;
- хранить:
  - `totalResource`;
  - `lastRunResourceRaw`;
  - `lastRunResourceGranted`;
  - `defeatPassives`;
  - `runsCount`;
  - `hpDefeatsCount`;
  - `arousalDefeatsCount`;
- реализовать save/load в простой файл;
- при отсутствии файла создавать дефолтное состояние.

Результат:

- база после перезапуска показывает сохраненные данные.

Критерии приемки:

- поврежденный save не приводит к crash;
- формат save простой и понятный;
- сохранение вызывается в одном месте result flow.

Рекомендация: для MVP можно использовать простой JSON через небольшую dependency или собственный line-based формат. Если не хочется добавлять dependency, line-based формат безопаснее для скорости прототипирования.

### Этап 15. Base stub и result UI

Цель: довести базу до требований MVP.

Задачи:

- на базе показывать:
  - кнопку/инструкцию start run;
  - общий ресурс;
  - результат прошлого забега;
  - список defeat passives;
  - базовую статистику;
- убрать любые намеки на строительство или upgrade tree;
- добавить result screen или result block перед возвратом на базу.

Результат:

- база является рабочим hub-stub;
- игрок понимает итог прошлого run.

Критерии приемки:

- база не содержит out-of-scope функционал;
- все значения берутся из `PersistentState`;
- старт нового run не сбрасывает общий прогресс.

### Этап 16. Балансировка и нагрузочный smoke-test

Цель: проверить, что ECS-подход выдерживает много сущностей.

Задачи:

- добавить debug-счетчики entities/projectiles/enemies;
- добавить временный stress режим спавна;
- проверить FPS при большом числе врагов и снарядов;
- найти самые дорогие системы;
- при необходимости добавить пространственную оптимизацию для поиска целей/коллизий.

Результат:

- понятны лимиты текущего прототипа;
- есть решение, нужна ли spatial grid уже в MVP.

Критерии приемки:

- при обычном MVP-наборе волн нет заметных просадок;

## 7. Риски и решения

### Риск: ECS станет слишком сложным

Решение: делать только минимальный ECS, нужный для MVP. Системы и компоненты должны быть очевидными, без попытки построить универсальный engine.

### Риск: коллизии и поиск целей будут дорогими

Решение: сначала использовать простой перебор, но изолировать его в `CollisionSystem` и target selection. После stress-теста при необходимости добавить spatial grid.

### Риск: UI экранов смешается с симуляцией

Решение: экраны управляют состоянием приложения, а ECS обновляет только run-сущности. Level up, stop и result должны ставить симуляцию на паузу.

### Риск: балансные значения окажутся разбросаны по коду

Решение: вынести стартовые числа из GDD в `Balance.h/.cpp` или data-структуры. Системы должны читать параметры из stats/config, а не хранить magic numbers.

### Риск: сохранение начнет ломаться при изменении формата

Решение: для MVP хранить минимальный persistent state и добавить version field, даже если формат простой.
